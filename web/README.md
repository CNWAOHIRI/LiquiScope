# LiquiScope — Live Demo Frontend

Minimal public MVP for the LiquiScope hackathon submission: paste (or pick) a
wallet address, get a live DeFi liquidation-risk report. Presentation only —
input → report, nothing else (no wallet-connect, no auth, no database).

**Engine note:** the "LiquiScope engine" referenced in Guardian Network's
marketplace listing did not exist as a standalone module anywhere in the repo
at the time this frontend was built (verified by full-repo search — see
project history). The risk-scanning engine (`lib/engine/`) was built from
scratch as part of this work, scoped to Aave V3 + Compound V3 across
Ethereum, Arbitrum, and Base, using on-chain reads only (viem + Multicall3,
no external price API). It lives inside `/web` rather than as a separate
top-level package — this was a deliberate simplification for one-command
Vercel deploys (a true monorepo package would need workspace config Vercel's
zero-config import doesn't pick up automatically). If this ever needs to be
reused outside the frontend, `lib/engine/` has no dependency on Next.js and
can be lifted out directly.

## What it checks

Aave V3 and Compound V3 borrow positions on Ethereum, Arbitrum, and Base for
a given address. For each open position: health factor, risk tier
(safe/warning/critical — thresholds match Guardian Network's own
HEALTHY/WATCH/DANGER/CRITICAL ladder, collapsed to 3 tiers), total
collateral/debt in USD, and the dominant collateral asset's current price,
liquidation price, and % drop-to-liquidation. A summary/action-plan is
generated by Claude (`claude-opus-4-8`) when `ANTHROPIC_API_KEY` is set,
falling back to a deterministic template otherwise (`summarySource` field
tells you which).

## Run locally

```bash
npm install
npm run dev
```

Open http://localhost:3000, paste an address, click Analyze. No env vars are
required to run.

### Environment variables (all optional)

| Variable | Purpose | If unset |
|---|---|---|
| `RPC_URL_ETHEREUM` | Ethereum mainnet RPC | Falls back through 3 free public endpoints, in order: `ethereum-rpc.publicnode.com` → `cloudflare-eth.com` → `eth.llamarpc.com` |
| `RPC_URL_ARBITRUM` | Arbitrum RPC | Falls back through: `arb1.arbitrum.io/rpc` → `arbitrum-one-rpc.publicnode.com` → `arbitrum.llamarpc.com` |
| `RPC_URL_BASE` | Base RPC | Falls back through: `mainnet.base.org` → `base-rpc.publicnode.com` → `base.llamarpc.com` |

Each chain uses viem's `fallback()` transport — if your custom `RPC_URL_*`
is set it's tried first, then the public list. A single flaky provider
(observed live: `eth.llamarpc.com` returning Cloudflare 521s) no longer
fails that chain's scan; it just moves to the next one in the list.
| `ANTHROPIC_API_KEY` | Enables the AI-generated summary | template fallback |

Public RPCs are rate-limited and occasionally return 5xx (observed live
during testing — see below); a per-chain failure doesn't fail the whole
scan, it just gets skipped and reported in `scan.chains[]`. For a more
reliable public demo, set your own RPC URLs (Alchemy/Infura/etc. free tiers
are plenty).

## Deploy to Vercel

1. Push this repo (or just the `/web` subtree) to GitHub.
2. In Vercel: **New Project** → import the repo → set **Root Directory** to
   `web`.
3. Framework preset auto-detects as Next.js — no build command changes
   needed.
4. Add environment variables in Project Settings → Environment Variables
   (all optional, see table above).
5. Deploy. No `vercel.json` is needed — the API route's
   `export const maxDuration = 20` (in `app/api/analyze/route.ts`) is picked
   up automatically by Vercel's Next.js integration.

Free-tier (Hobby) function timeout is enough headroom: the 6 sub-scans
(3 chains × Aave + Compound) run in parallel via `Promise.allSettled`, so
wall time is roughly the slowest single chain's RPC round-trip, not the
sum — observed **~0.6–1.3s** end to end in local testing (see below), well
under the 20s budget even with one RPC failure in the mix.

## What was actually tested

`npm run build` passes clean (TypeScript + ESLint, zero errors/warnings).
`npm run dev` was started and exercised live:

- `POST /api/analyze` against Guardian Network's own monitored address
  (`0xd3400E9b08977463677A21B838dD2eCEFf1d8139`, Aave V3 Base) returned a
  real `overallRiskTier: "none"` — independently cross-checked directly
  against the Aave Pool contract (`getUserAccountData`), confirming the
  position currently has zero collateral and zero debt (it was closed out
  since the repo's own docs were written). This exercised the full call
  chain — `PoolAddressesProvider` → `Pool` → `getReservesList` — end to end
  against live Base RPC.
- The same request's Ethereum sub-scan hit a real `521` from the free
  `eth.llamarpc.com` endpoint — this is exactly the kind of failure the
  per-chain error isolation (`Promise.allSettled` + `scan.chains[]` status)
  is designed for: the response still came back `200` with Arbitrum and
  Base results intact, Ethereum reported as `status: "error"` with the raw
  message, and the UI's error footer surfaces "N chain read(s) failed and
  were skipped" instead of a blank page.
- Arbitrum and Base both completed real on-chain multicall reads for **both**
  Aave V3 and Compound V3 without error, confirming the hardcoded
  `PoolAddressesProvider` and Comet market addresses resolve correctly.
- The liquidation-drop formula was verified standalone against a hand-worked
  algebraic check (independent of any RPC call) — see project history for
  the derivation and the passing sanity check.
- The full report page (`GET /`) renders with correct title and UI chrome
  with zero server errors in the dev log.

**Not yet exercised live:** the `positions.length > 0` render path (risk
badge on non-"none" tiers, position cards, dominant-collateral math against
a real indebted wallet). The test address's position was closed since the
repo's docs were written, and I didn't go hunting for a real stranger's
distressed position to use as a demo case. Per the task, this is exactly
what the 3 preset example addresses are for — paste your known critical
Arbitrum test address (or fill in `EXAMPLE_ADDRESS_1/2/3` in `app/page.tsx`)
and confirm the styled report end to end before calling this fully done.

## Risk monitor (`/api/monitor`)

A thin loop over the frozen engine — `lib/engine/` is untouched by this
feature, same rule as the rest of this app. Periodically re-scans a small
watchlist and sends a Telegram alert when a wallet's tier changes.

**How it works:**

1. `GET /api/monitor`, protected by an `x-monitor-secret` header matching
   `MONITOR_SECRET` — rejects with `401` without it, `500` if the server
   itself has no `MONITOR_SECRET` configured (fails closed, never open).
2. For each address in the watchlist (`lib/watchlist.ts` — env var
   `WATCHLIST_ADDRESSES`, comma-separated, or defaults to the 3 example
   addresses on the report page), calls `analyzeWallet()` — the same frozen
   engine entry point the UI uses — and compares the resulting tier to the
   last-known tier in Upstash Redis (Vercel Marketplace, free tier).
3. Sends a Telegram message via the bot API on:
   - **A brand-new address** (no prior KV state) — a plain "now monitoring"
     message, never a fake transition.
   - **An actual tier change** (e.g. `WARNING -> CRITICAL`).
   - **A wallet stuck at CRITICAL for >6h** (`CRITICAL_REALERT_HOURS`,
     default 6) — the one deliberate exception to "no duplicate alerts",
     so a real emergency doesn't go silent just because nothing "changed."
   - **>3 consecutive scan failures for one address** (every chain read
     erroring) — silent monitor death is worse than no monitor.
4. Updates KV after every run regardless of whether an alert fired, so
   `lastChecked` always reflects the most recent pass.

**Frontend touch:** `POST /api/analyze` (not the engine) now also checks
`isWatched()` + reads KV, and the report page shows a small "👁 Monitored ·
last checked Xm ago" pill under the risk badge for watchlist addresses. No
watchlist management UI — that's explicitly out of scope until asked for.

### Scheduler — GitHub Actions, not Vercel Cron

`.github/workflows/liquiscope-monitor.yml` runs every 5 minutes
(`workflow_dispatch` also enabled for on-demand testing) and just curls
`/api/monitor` with the secret header. **GitHub Actions' `schedule` trigger
is best-effort** — GitHub's own docs note scheduled runs can slip 5-15
minutes (sometimes more) under platform load. That's fine for a
liquidation-risk monitor; it is not a guarantee for anything time-critical.

Vercel Cron was deliberately **not** used — Hobby tier cron jobs are
effectively daily-granularity, nowhere near the 5-minute cadence this needs.

Requires two GitHub repo settings (Settings → Secrets and variables →
Actions):

| Name | Type | Value |
|---|---|---|
| `MONITOR_SECRET` | Secret | Same value as the Vercel env var |
| `MONITOR_URL` | Variable | `https://<your-deployment>.vercel.app/api/monitor` |

### Environment variables (monitor-specific)

| Variable | Purpose | Required? |
|---|---|---|
| `MONITOR_SECRET` | Shared secret the caller must send as `x-monitor-secret` | Yes — route 500s without it |
| `TELEGRAM_BOT_TOKEN` | Bot token for `api.telegram.org/bot<token>/sendMessage` | Yes for alerts to actually send (route still runs and updates KV without it — `sendTelegramAlert` just returns `{ok:false}`) |
| `TELEGRAM_CHAT_ID` | Destination chat | Yes, same caveat |
| `WATCHLIST_ADDRESSES` | Comma-separated addresses | No — defaults to the 3 example addresses |
| `CRITICAL_REALERT_HOURS` | Re-alert cadence while stuck CRITICAL | No — defaults to 6 |
| `APP_URL` | Included in alert messages | No — defaults to the known production URL |
| `KV_REST_API_URL` / `KV_REST_API_TOKEN` (or `UPSTASH_REDIS_REST_URL` / `_TOKEN`) | Upstash Redis credentials | Yes — route 500s without KV configured. Auto-injected by `vercel integration add upstash/upstash-kv` |

### Why Upstash Redis, and what it costs

Free tier: 256MB storage, 500K commands/month. At 5 watchlist addresses ×
~2 KV ops × 288 runs/day (5-min cadence) ≈ 173K commands/month — comfortably
under the cap with room to grow. Installing it via
`vercel integration add upstash/upstash-kv` requires a one-time browser
click to accept Upstash's marketplace terms (`vercel integration
installations` to confirm it went through) — that step can't be done from
a CLI/agent session non-interactively.

## Project structure

```
web/
  app/
    page.tsx                 — single-page UI (idle/loading/error/success states)
    api/analyze/route.ts      — POST: validate → rate-limit → scan → attach monitor status → respond
    api/monitor/route.ts       — GET: secret check → per-address scan → tier-diff → alert → KV write
    components/               — RiskBadge, SummaryPanel, PositionCard, ReportSkeleton
  lib/
    engine/                   — the scanning engine (chain-agnostic, no Next.js deps, FROZEN)
      chains.ts                — per-chain RPC + contract address config
      aave.ts                   — Aave V3 scanner
      compound.ts                — Compound V3 (Comet) scanner
      tiers.ts                    — risk-tier thresholds
      summary.ts                   — AI summary + template fallback
      index.ts                      — analyzeWallet(address) → Report
    abi/                      — minimal ABI fragments (only the functions actually called)
    rateLimit.ts               — in-memory 5 req/min/IP limiter
    watchlist.ts                — monitor watchlist config
    kv.ts                        — Upstash Redis client + monitor-state read/write
    telegram.ts                   — sendMessage helper
.github/workflows/liquiscope-monitor.yml — 5-min best-effort cron, curls /api/monitor
```
